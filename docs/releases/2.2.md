# Dekan 2.2 source integration

## Status

The source and supplied-binary integration is prepared for local Windows compilation. The maintainer supplied the newer launcher and bridge DLL and approved keeping their internal protocol names while retaining Dekan branding. This is not a claim that Windows loading or a match was tested here.

The obsolete native bridge/launcher source crates have been removed from the workspace. The app packages the supplied hash-pinned binaries from `vendor/native`, with public Dekan filenames and the hidden compatibility DLL alias required by the launcher. The adapter discovers the current bridge identity instead of reusing the old service. See ADR-032.

## Integrated changes

- Bounds-checked skeleton/mesh rebuilding for base-skin assets.
- Base-skin audio event/tag normalization and leftover numbered-skin event removal.
- Classic Rift slot-zero identity rebasing and generation cache invalidation.
- Additional model/audio audit coverage, Zed chroma cases and `harness --champ` filtering.
- Workspace and local lockfile versions stamped to `2.2.0` by the existing version implementation; display version remains `2.2`.

## Dekan customizations

The app starts from the supplied Dekan 2.1 tree, retaining its logos, icons, banner, screenshot assets, Classic/Crimson/Obsidian themes, Turkish/English dictionaries, theme persistence, party relay and DNS recovery, Discord Rich Presence, webhook handling, update trust anchor and release workflow configuration.

The GitHub star gate, update repository and product links remain configured for `chrisssst/Dekan`. The MIT identity, product metadata, installer and crate names use Dekan. No new dependency was introduced, and all 640 registry lockfile records remain identical to the original source.

The private release signing key and repository-level secrets are not exported by GitHub into a source archive. Existing references and configuration are retained; no new key or webhook is generated.

## Checks performed on Linux

- Existing version module: three tests passed; its stamping function set the manifest and local lock records to 2.2.0.
- `cargo metadata --locked --no-deps --format-version 1`: the original 12 workspace packages reported 2.2.0; after retiring two obsolete native crates, all 10 remaining members report 2.2.0.
- `cargo fmt --all -- --check`: passed.
- Final original discarded-Result sweep: 426 justified, zero unexplained.
- Final original source-size sweep: 490 code files; no file over 400 lines or leaf directory over five files.
- Final original comment sweep: 526 files, zero prohibited comments; 459 tool directives retained.
- `cargo test --locked -p dekan-classic --target x86_64-unknown-linux-gnu`: 120 passed.
- `cargo test --locked -p dekan-core -p dekan-wad -p dekan-party --target x86_64-unknown-linux-gnu`: 187 passed, one live relay test ignored.
- `cargo clippy --locked -p dekan-classic -p dekan-core -p dekan-wad -p dekan-party --all-targets --target x86_64-unknown-linux-gnu -- -D warnings`: passed.

Conditional live-game tests do not prove game compatibility when the game is absent. No match or launcher/bridge runtime behavior has been verified here. A source archive is provided, not a newly built or verified Windows installer.

## Native adapter checks

A temporary Linux harness compiled the actual production discovery, client and native-bundle source modules, the real error types and the existing client tests. Only the Windows process lookup boundary was replaced by a no-process test shim. The harness uses the project's declared Rust 1.85 MSRV. Clippy with `-D warnings` passed for these source modules. Ten tests passed: current hello identity/PID acceptance, rejection of the obsolete identity and failed hellos, authenticated TCP command flow and nested manager responses, rejection of a modified payload, and packaging/alias creation with stale/missing-file rejection. This does not execute the supplied Windows binaries.

The supplied payloads remain byte-identical to the uploads. The source tree and installer expose Dekan product/tool names; internal binary strings and the compatibility alias retain the protocol names authorized by the maintainer.

## Windows verification before release

Use the existing Windows x64 MSVC environment:

```powershell
cargo xtask check
cargo xtask package
cargo xtask installer
```

The expected installer name after a successful real build is `dist/installer/Dekan-Setup-2.2-x64.exe`. The uploaded 2.1 installer is a reference only; it must not be renamed or represented as a 2.2 build.

Keep the existing GitHub `RELEASE_SIGNING_KEY` secret and OAuth/webhook variables in place. Signing and verification must continue with the existing trust anchor. Complete Windows checks, the injector handshake, party/DNS recovery and a real-match test before publication.
